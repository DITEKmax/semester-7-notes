# RecyclerView, Jetpack Compose, состояние и адаптивность

## Эффективные списки: RecyclerView

Если коллекция намного длиннее экрана, не нужно создавать отдельный View для каждой записи: одновременно пользователь видит только часть списка. RecyclerView использует ограниченное количество представлений и повторно назначает их новым элементам при прокрутке. Видимые элементы отображаются, ушедшие за экран могут быть переиспользованы, а в них помещаются данные следующих записей. Это уменьшает потребление памяти и вычислений.

В работе участвуют несколько частей. RecyclerView запрашивает элементы, Adapter получает коллекцию, создаёт или подготавливает View и связывает представления с данными, а LayoutManager определяет их расположение. LinearLayoutManager формирует линейный список; GridLayoutManager — сетку с заданным числом столбцов. При создании менеджера передают context — часть приложения, в которой выполняется операция; для UI это часто Activity или Fragment.

При изменении коллекции нежелательно пересоздавать весь список. ListAdapter может сравнить старую и новую версии коллекции, найти добавленные, удалённые и изменившиеся элементы и обновить только необходимые части.

## Compose описывает UI функциями

В XML интерфейс задан разметкой; в Compose он описывается Kotlin-функциями с аннотацией @Composable. Такие функции принимают данные, создают компоненты и вызывают другие composable-функции, формируя иерархию. Activity передаёт корневое содержимое через setContent; внутри можно обернуть экран темой и вызвать нужные UI-функции.

Компоненты Compose выполняют знакомые задачи: Text отображает текст, Button принимает нажатие, TextField и OutlinedTextField вводят текст, Image показывает изображение; также есть переключатели и индикаторы. Кнопка получает обработчик, а её видимое содержимое задаётся вложенным блоком.

Column располагает элементы вертикально, Row — горизонтально, Box задаёт общую область, где элементы могут накладываться. Например, Button и Text можно вызвать последовательно внутри Column; вложенность функций становится вложенностью элементов интерфейса.

### Modifier и порядок преобразований

Modifier задаёт размер, оформление и часть поведения элемента: fillMaxWidth() занимает доступную ширину, size(...) задаёт желаемый размер, padding(...) добавляет отступ, background(...) задаёт фон, clickable(...) добавляет нажатие обычному элементу. Вместо огромного числа самостоятельных параметров компонента свойства собираются в цепочку.

Порядок в этой цепочке влияет на результат. Если применить background, затем padding, фон и отступ взаимодействуют одним образом; если сначала добавить padding, а затем фон — окрашенная область будет другой. Одинаковый набор модификаторов в другом порядке может дать иной UI.

## Наблюдаемое состояние, композиция и callbacks

Compose строит отображение вокруг состояния. Обычная локальная переменная может получить начальное значение при повторном выполнении функции, поэтому UI-значение, которое должно пережить рекомпозицию, сохраняют специальным способом. remember удерживает его между рекомпозициями, пока соответствующий вызов остаётся в композиции. В счётчике значение начинается с нуля, хранится через remember и увеличивается при нажатии, не сбрасываясь при каждом выполнении функции. Это состояние UI, а не база данных.

Композиция — выполнение composable-функций и построение UI. Рекомпозиция — повторное выполнение нужных частей описания после изменения состояния, от которого они зависят. В примере со счётчиком пользователь нажимает кнопку, состояние меняется, читающий его участок обновляется, и новое число отображается. Это не перезапуск приложения и не пересоздание Activity; обновляться может лишь зависящий элемент, а не весь экран.

rememberSaveable нужен для небольшого значения, которое желательно восстановить после пересоздания или возврата экрана, например введённого пользователем значения. Он не заменяет базу данных и не предназначен для больших объёмов данных.

Компонент может получать данные через параметры, а действия сообщать наружу функцией или callback. Например, компонент счётчика получает count и onIncrement. Визуальная часть показывает значение и вызывает переданное действие, не обязуясь знать, где хранится состояние и как устроена прикладная логика. Владелец состояния хранит и меняет данные, затем передаёт значения и callbacks вниз. Если состояние нужно нескольким дочерним элементам, его поднимают выше в иерархии: такой владелец передаёт каждому компоненту необходимые данные и действия. Компоненты от этого становятся проще и пригоднее к повторному использованию.

## Большие коллекции, модели данных и preview

Для крупных коллекций в Compose используются lazy-компоненты: LazyColumn для вертикального списка, LazyRow для горизонтального и lazy grid для сетки. По назначению они похожи на RecyclerView: большой набор отображается эффективно, а не создаётся целиком заранее.

В примере элемент описан Kotlin data class — классом для набора свойств объекта. Коллекция таких объектов передаётся в items; каждый элемент преобразуется в UI, например название продукта отображается через Text. Сетка может быть адаптивной: задаётся минимальная ширина элемента, после чего система вычисляет, сколько колонок помещается в доступное пространство.

Предварительный просмотр компонента задаётся через @Preview. Можно подготовить несколько preview с разными данными, состояниями, размерами или параметрами текста. Если элемент ожидает callback, а в preview действие не требуется, ему передают пустую лямбду.

## Одинаковое управление состоянием в View и Compose

Пример счётчика показывает общий принцип. В XML/View хранится count, кнопке назначают listener, он увеличивает число, затем код вручную меняет текстовый View либо вызывает render(). В Compose хранится наблюдаемое состояние, Text читает его, кнопка меняет его, а Compose повторно строит зависимый участок. Событие и данные одинаковы; различается синхронизация интерфейса с ними.

В форме ввода изначально пустое поле и текст «Введите имя»; после ввода показывается приветствие с именем. В View обработчик изменения текста обновляет значение и текстовый элемент. В Compose TextField хранит состояние, обработчик задаёт новое значение, и зависимый Text обновляется при рекомпозиции.

При удалении элемента новая коллекция строится фильтрацией по ID: остаются записи, чей идентификатор не равен удаляемому. В RecyclerView новую коллекцию передают адаптеру, который вычисляет разницу; в Compose новая коллекция становится состоянием, от которого зависит lazy-список.

Общий поток можно выразить так: владелец хранит состояние; UI получает данные; действие пользователя вызывает событие; UI передаёт его владельцу; владелец меняет состояние; UI показывает новое значение. В XML структура задана разметкой, доступ идёт через ссылки или binding, действия — через listeners, обновление — через изменение свойств View. В Compose структура строится функциями, данные поступают параметрами, действия идут через callbacks, отображение обновляется по состоянию и рекомпозиции. В обоих подходах прикладную логику нужно отделять от деталей UI; передача данных и callbacks особенно облегчает это в Compose.

## Темы, строки и локализация

Функциональности недостаточно для хорошего UI. Material Design задаёт общие правила цветов, типографики, форм компонентов и других параметров. В XML темы и стили хранятся в ресурсах, а элемент ссылается на атрибут темы, фактическое значение которого определяется текущей конфигурацией. В Compose содержимое оборачивается темой Material или Material 3, передающей палитру, типографику и другие значения дочерним компонентам. Учитываются светлая и тёмная схемы.

Текст интерфейса не следует повторять в каждом компоненте. Строковые ресурсы централизуют значения, позволяют переиспользовать и локализовать их; один ключ может иметь разные значения для разных языков. Android выбирает ресурс по локали устройства. Перевод может заметно изменить длину фразы, поэтому экран должен выдерживать длинные подписи, иной размер текста и правила множественного числа. Нельзя рассчитывать, что строка всегда имеет одну фиксированную длину.

## Адаптация к реальному окну

Android работает на смартфонах, планшетах и складных устройствах, при разных ориентациях и в многооконном режиме. Размер окна может меняться во время работы, поэтому интерфейс адаптирует расположение элементов, число столбцов и состав видимых областей.

Часть экрана занята системными областями: статус-баром, навигацией, вырезами и отверстием камеры. Важные элементы не должны оказаться перекрыты; при компоновке учитывают системные insets.

Появление экранной клавиатуры также меняет доступное пространство. Нужно проверить, видно ли активное поле, доступны ли нужные действия и не закрыта ли кнопка, а экран корректно перестроился. Проверки только статического экрана без клавиатуры недостаточно.

В лекции отдельно обсуждается edge-to-edge: современные Android-интерфейсы используют область вплоть до системных границ. Упоминаются Android 15 и target SDK 35; в этом контексте обработка системных отступов представлена как необходимая часть компоновки, а не декоративная настройка.

## Итог

RecyclerView показывает эффективную работу с большими списками в View-системе. Compose описывает интерфейс декларативно через функции, наблюдаемое состояние и рекомпозицию. В обоих подходах события меняют данные, а отображение должно следовать за состоянием. Кроме управления состоянием, интерфейсу нужны отделение логики от UI, адаптивные размеры, темы и строки для локализации, учёт системных областей, клавиатуры и реального размера окна.
